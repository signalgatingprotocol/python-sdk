# Fresh executive comparisons

This is a small synthetic comparison harness for the experimental executive API.
It runs actual typed worker episodes, owner controls, local effects, artifact
reads, independent exact-byte checks, durable receipts, and journal reconstruction.
The default worker is an arithmetic fixture that does not know which arm it is running under. A tie between arms is a valid result.
Neither passing fixtures nor these planning thresholds establish model quality,
security protection, inference savings, or general superiority.

Run from a source checkout or an installation containing the executive module:

```bash
python -m signal_gating.executive.evaluation \
  --cases examples/executive/evaluation/cases.jsonl \
  --protocol examples/executive/evaluation/protocol.json \
  --output /tmp/executive-comparison.json
```

No credentials, optional provider SDK, subprocess checks, or network are needed.
The command prints the maximum planned model requests before starting. It writes
all attempts, receipts, measured resources, unknowns and failures to JSON. Each
attempt retains its own temporary store and artifacts at `result.store_path`.
These paths are intentional evidence retention. Remove them yourself when the
report is no longer needed. The CLI returns 0 when it writes the complete report,
even if cases or usefulness criteria fail. Configuration rejection returns 2.
Read `comparison.criteria_met` and every result before making an outcome claim.

## Frozen protocol

The committed canonical manifest digest binds all 30 complete typed cases,
including initial records, operator stimuli, expected dispositions and completion
IDs. `protocol.json` names six tuning cases and 24 held-out cases. Each category
has one tuning and four held-out cases: correction, interruption/resumption,
contradictory evidence, repeated failure, restart/unknown effect, and low overhead.
There are three trials per held-out case, hence 72 attempts per arm, 360 overall.
Only the held-out split runs through this CLI. Use `evaluate_cases` on the named
tuning split for development. Freeze a new explicit protocol version before a
future live evaluation if cases change. No live evaluation has been run here.

Trial order is case-manifest order, then trial 0/1/2, then the next case. Arms run
in the listed protocol order. Each attempt constructs a fresh supplied worker and
fresh store. Nothing is learned or carried between trials. This fixed arm order
is reproducible but can confound a future live run with provider/time drift;
report that limitation or prospectively freeze a balanced order in a new protocol.
The simulated stimulus clock advances only explicit retry-backoff stimuli. Wall
measurements use `perf_counter_ns`, separately from simulated time.

Inputs with `evaluation.*` kinds form a small, closed instruction language that only the operator can load.
They drive owner commands inside this program. Generic runtime observations or
model output cannot enter this path or become owner authority. The harness never
loads an arbitrary authoritative state snapshot: initial owner/goal/commitment/
task definitions go through real `CreateGoal` commands. Evidence goes through
real artifact publication, explicit sharing and owner evidence notifications.
Expected IDs/dispositions score observed outcomes only; they never create proof.
Wrong generated bytes cannot complete merely because a case expects completion.

## Arms and common safeguards

All arms use the same worker/model, two exact rendered messages, tools, principal
bindings, goal limits, context/output caps (16,384/1,024 capacity units), hard local
requirements, grants, verification, failure limits, stimuli and trial order.
Each arm gets at most eight real worker invocations. All arms run on the same
real Kernel, which enforces the same authority, budget, and verification checks
for each of them. These are different operational
controllers running on the same Kernel, not independently implemented safety kernels.
Baselines also receive the full mandatory authority/task/requirement context.
This conservatively strengthens them; it does not give executive extra authority.

| Arm | Actual behavior |
| --- | --- |
| `notes` | Writes bounded operational notebooks from actual control receipts and resume notes. Compacts older operations into a count plus four recent entries. Keeps the full current outcome and all mandatory hard requirements. Retains the newest notebook, fills optional evidence by recency, and uses FIFO within ordinary slots. |
| `rules` | Adds an explicit current task plan with status, priority, pending effects and next work/wait state. Deduplicates equivalent operational entries before compaction. Uses priority scheduling and bounded chronological evidence. This semantic notebook dedup is additional to common durable delivery idempotency. |
| `executive` | Uses the existing evidence-linked/supported context selection, journal-backed task state, attention, priority, aging and reconciliation scheduling. |
| `executive_no_memory_gating` | Uses bounded chronological optional working-context selection. It retains authoritative memory admission, disputes, freshness, proof and permissions. |
| `executive_no_priority_scheduling` | Uses FIFO within eligible ordinary slots. Owner controls, urgent/reconciliation classes, quotas, capacity and freshness stay enforced. |

The protected context-ordering hook runs only on optional candidates. Mandatory
refs never enter it. Every selection still passes the same ACL, integrity and
capacity checks, actual message counting, staged artifact persistence and full
admission CAS. No text is changed after build. Observational verification refs
retain their as-of-admission meaning; they do not become action dependencies,
proof or permission. Old notebooks remain auditable but do not fill current
working context after compaction. There is no unrestricted-history baseline.
The chronological ablation can still include a small linked checkpoint after
larger candidates overflow; this is the size limit working as designed, not a defect in the ablation.

The arithmetic fixture computes from the actual current trusted goal. It does
not consult expected completions or the arm name. Contradictory source records
and context pressure exercise real evidence requests and ordering. The low-overhead category includes two competing goals and duplicate informational wakes,
making FIFO/priority and notebook dedup observable. Two cases deliberately return valid but empty EpisodeResults. They exercise how the kernel handles no progress: backoff, blocking after repeated failures, and owner correction.
Actual no_progress episode receipts are retained after recovery. This measures
controlled robustness, not provider reliability or a real provider-error rate.
Workers that skip these instructions fail the category, even if arithmetic completes. The restart category creates a marker
exclusively once, deliberately reports an unknown effect, restarts the store,
then requires actual owner reconciliation of marker bytes. The restart category passes only with the actual unknown state, exactly one
effect/dispatch, and successful owner reconciliation. Arithmetic completion alone
cannot satisfy it. No blind retry occurs.
All artifacts and side effects are local to the attempt directory.

## Measurements and acceptance

`EvaluationResult.passed`, its actual `summary`, and the existing read-only
`completed` projection retain their meanings. A recoverable failed worker call
can appear in `failures` while the case later passes. Failed invocations,
constructor failures, rejected proposals, unknown usage and failed cases are
retained. Reusing a factory's worker instance is rejected to prevent trial leakage.
The summary remains the real Kernel summary; resource measurements do not rewrite
its authoritative completion state.

`worker_calls` counts actual worker invocations; `verifier_calls` counts actual
independent local checks. `control_calls` counts actual host control/admission/
run/notification operations, notebook publications, store lifecycle operations,
and local adapter calls. `tool_calls` is also shown separately. Thus
`total_calls = worker_calls + control_calls + verifier_calls`; these heterogeneous
local operations are **not** all model requests. Planned paid request ceilings
count worker requests only. Individual provider `usage_observations` survive even
when a total quantity is unknown. Missing usage never becomes zero. Monetary microunits retain integer precision;
estimated charges do not become observed costs.

Attempt wall, worker, verifier and tool scopes are measured. Control overhead is
wall time outside the union of those dispatch scopes, including local bootstrap,
storage, preparation and shutdown. Awaited scopes can overlap; `overlap_seconds`
records that overlap, so scope sums need not equal wall time. Control work during
a provider await is not separately profiled as CPU. Context bytes are counted from
actual messages. Fixture workers use no model tokens and have zero trusted local
monetary charges. Those zero inference-token/cost values are fixture accounting,
not measured inference savings. These local wall measurements are not model
latency or a portable performance benchmark. The frozen Task16 demo is not run.

A future observed run can use the planning criteria only when all five arms have
the exact balanced held-out set and all three paired trials:

* Zero observed unauthorized effects or hard-constraint violations.
* At least 90% correct eligible resumption, with original commitments preserved.
* Verified completion at least as high as the stronger notes/rules baseline.
* Either 10 percentage points higher verified completion or 20% lower total
  observed cost at equal-or-better completion.

Completion differences and resource differences use paired case/trial observations.
Intervals use a fixed-seed 2,000-draw case-cluster bootstrap, retaining dependence
between each case's trials. They are descriptive uncertainty on this small suite,
not a proof of general superiority. Unknown cost anywhere blocks cost claims.
Zero baseline cost cannot establish a percentage saving. Synthetic scope always
blocks benefit claims. Empty or unpaired suites, replay results and tuning-only
comparisons cannot satisfy the usefulness gate. Failure blocks benefit claims and
expansion, not honest availability of the experimental code.

## Optional live worker

The default committed protocol has `live: null`, so `--live` fails before client
construction. No paid run is part of tests or this implementation. To plan a
future authorized run, copy the protocol and provide a `live` object containing:

```json
{
  "model": "OPERATOR_SELECTED_MODEL",
  "api_key_env": "OPERATOR_SELECTED_ENV_NAME",
  "quote": {
    "input_tokens": 16384,
    "output_tokens": 1024,
    "calls": 1,
    "elapsed_seconds": 30,
    "cost_microunits": 100000,
    "currency": "USD"
  },
  "quote_version": "OPERATOR_VERIFIED_VERSION",
  "quote_source": "OPERATOR_VERIFIED_MAXIMUM_SOURCE",
  "suite_cost_microunits": 288000000,
  "suite_request_limit": 2880
}
```

These amounts are **illustrative operator budget maxima**, not provider prices
or a recommendation to spend. Set a verified maximum quote and affordable suite
ceilings yourself. The quote must cover the configured input/output caps, one
request and positive finite elapsed/cost maxima. The suite ceilings must cover
24 cases × 3 trials × 5 arms × 8 requests = **2,880 planned maximum requests** and
the corresponding quoted cost before construction. The CLI prints those ceilings
and requires `--live`. It then constructs the existing optional `OpenAIWorker`
with retries disabled and the explicit model/quote provenance. Its actual model
responses drive the same proposal, tool, budget and verification path. It closes
every provider transport, including failed attempts. Real provider charges and
usage can remain unknown even with a maximum quote; this is not a spending sandbox.
Standard provider responses may omit authoritative billing totals. Their unresolved
usage holds can prevent verified completion; the harness never settles a quote as
an observed bill. Do not put credential values in protocol files or output.

Programmatic API:

```python
report = await evaluate_cases(cases, arm="executive", trials=3,
                              worker_factory=fresh_worker_factory)
comparison = compare_reports(reports)
```

A supplied factory is actually invoked once per attempt. It must return fresh,
trusted free local Workers, or already operator-authorized bounded OpenAIWorkers.
The caller owns preconstruction consent and suite ceilings outside the CLI. Custom
unmetered workers are conservatively labeled synthetic. The protected instance
meter preserves the actual bounded OpenAI adapter/quote checks and supplied method;
there is no global monkeypatch or model substitution. Actual optional SDK
construction is a separate installed integration gate, not exercised by fixtures.
Reconstructing retained journals with `reducers.rebuild` is read-only replay
inspection. It is distinct from a fresh worker evaluation; `compare_reports`
rejects reports tagged `evaluation_kind="replay"`.
